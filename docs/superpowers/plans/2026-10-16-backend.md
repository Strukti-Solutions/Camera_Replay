# Backend: schema, API do botão, fila de clipes, R2 e limpeza

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** O app Next.js recebe o aperto do botão, grava aperto e clipe `pendente` no Postgres com isolamento entre arenas, expõe a fila de clipes ao worker como funções SQL, assina URLs de leitura no R2 e apaga os clipes expirados.

**Architecture:** As regras que precisam ser atômicas ficam em **funções SQL** dentro das migrações (`registrar_aperto`, `pegar_clipes`, `marcar_pronto`, `marcar_falhou`, `expirar_presos`). Assim o app TypeScript e o worker Python chamam o mesmo contrato, e o adaptador Python vira uma casca fina. O TypeScript fica fino: rotas em `app/api/`, lógica em `app/lib/`, tudo recebendo um `Db` injetado (`pg.Pool` em produção, PGlite nos testes). O isolamento entre arenas é garantido por **chaves estrangeiras compostas** `(id, arena_id)`, não só por `WHERE`.

**Tech Stack:** Node 24, Next.js 15 (App Router, route handlers), TypeScript 5.9, `pg` 8, `zod` 4, `aws4fetch` 1, Vitest 5, `@electric-sql/pglite` (Postgres em WASM, só nos testes). Mesmas versões fixadas do `C:/Codes/strukti-site/package.json` quando o pacote existir lá.

**Spec:** `docs/superpowers/specs/2026-10-16-replay-saas-design.md`. Código de origem do R2 (somente leitura): `C:/Codes/strukti-site/src/lib/bancada/r2.ts`.

**Branch:** `feat/backend`, criada a partir de `main`.

## Global Constraints

- Toda tabela filha carrega `arena_id`, e toda consulta filtra por ele.
- O app e o worker se falam **pelo Postgres**, nunca por HTTP direto.
- O aperto grava o instante do servidor: `recebido_em = now()` do banco. O relógio do ESP32 não entra.
- Aperto duplo: dois apertos do mesmo botão com menos de **5 s** de intervalo viram um só.
- Clipe `pendente` ou `processando` há mais de **2 minutos** (contados de `recebido_em`) vira `falhou`.
- Expiração padrão: **7 dias** (`arenas.dias_retencao`, default 7).
- Token do botão: só o hash SHA-256 (hex) vai para o banco. O token tem 32 bytes aleatórios em base64url. Tokens revogados (`revogado_em` preenchido) são recusados.
- Credenciais da câmera: cifradas com AES-256-GCM. A chave vem de `CAMERA_CRED_KEY` (32 bytes em base64).
- Bucket R2 privado. A URL assinada de leitura vale **15 minutos**.
- Dependências npm com versão **exata** no `package.json` e publicadas há pelo menos **7 dias** (quarentena).
- `.env`, `.env.local` e credenciais nunca entram no git.
- Comentários em português. Commits em Conventional Commits, com `git add` explícito e a linha final `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Testes: `npm test` na raiz do repo (Vitest). Os testes do worker continuam com `cd worker && py -m pytest`.

## Review Focus

- **Dois apertos simultâneos do mesmo botão** (o ESP32 repete o POST por timeout): só um clipe nasce. `registrar_aperto` trava a linha do botão com `FOR UPDATE`, e o segundo vê o primeiro. Teste com duas chamadas em sequência dentro de 5 s. (Tarefa 3)
- **Botão de uma arena apontando para câmera ou quadra de outra arena** (erro no painel ou ataque): o banco recusa o insert pela FK composta. (Tarefa 2)
- **Worker termina um clipe que o reaper já marcou `falhou`**: `marcar_pronto` não ressuscita o clipe e devolve `false`. (Tarefa 5)
- **Token ausente, malformado ou com espaços** no `Authorization`: 401, sem consulta que diferencie "não existe" de "revogado". (Tarefa 4)
- **R2 fora do ar na limpeza**: o clipe que não foi apagado no R2 continua no banco para a próxima rodada, e os outros seguem. (Tarefa 7)

  - SQL `registrar_aperto(p_token_hash text) returns table (clipe_id uuid, duplicado boolean)`.
  - `registrarAperto(db: Db, token: string): Promise<{ clipeId: string; duplicado: boolean } | null>` em `app/lib/aperto.ts`. Devolve `null` quando o token é inválido ou foi revogado.

Algoritmo de `registrar_aperto` (plpgsql). É a parte que o teste sequencial não prova sozinha, por isso vai descrito aqui:
1. `select ... from botoes where token_hash = p_token_hash and revogado_em is null for update`. Se não achar, `return` vazio.
2. `update botoes set visto_em = now()`.
3. Se existe aperto desse botão com `recebido_em > now() - interval '5 seconds'`, devolve o clipe desse aperto com `duplicado = true`.
4. Senão, insere o aperto e o clipe (`status 'pendente'`, `camera_id` do botão, `recebido_em` igual ao do aperto, `expira_em = recebido_em + dias_retencao da arena`) e devolve `duplicado = false`.

O `FOR UPDATE` do passo 1 é o que serializa dois POSTs simultâneos do mesmo botão.

### Task 7: Limpeza de expirados e rota de cron

**Files:**
- Create: `app/lib/limpeza.ts`, `app/api/cron/limpeza/route.ts`
- Test: `tests/limpeza.test.ts`

**Interfaces:**
- Consumes: `Db` (Tarefa 2), `expirar_presos` (Tarefa 5), `criarR2` e `lerConfigR2` (Tarefa 6).
- Produces:
  - `limparExpirados(db: Db, r2: { apagar(chave: string): Promise<void> }, limite = 500): Promise<{ apagados: number; erros: number; presos: number }>`.
  - `criarHandlerLimpeza(db, r2, segredo: string | undefined): (req: Request) => Promise<Response>`.

Comportamento:
1. Chama `expirar_presos()` e guarda o número em `presos`.
2. Seleciona até `limite` clipes com `expira_em < now()`.
3. Para cada um, apaga no R2 (se tiver `chave_r2`) e depois apaga a linha. Se o R2 falhar, conta em `erros`, mantém a linha e segue para o próximo.

A rota exige `Authorization: Bearer <CRON_SECRET>`, comparado com `timingSafeEqual`. Responde 401 sem o segredo, 503 se `CRON_SECRET` ou o R2 não estiverem configurados, e 200 com o JSON do resultado. Exporte `GET`, porque o cron da Vercel usa GET.

test("rota: 401 sem Bearer, 401 com segredo errado, 200 com o certo, 503 sem CRON_SECRET", ...)
